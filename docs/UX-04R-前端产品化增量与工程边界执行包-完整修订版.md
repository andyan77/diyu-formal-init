## 一、定位：不是“美化现有聊天框”，而是有界重建用户决策顺序

当前前端的主要问题不是颜色或圆角，而是把后端调用顺序直接暴露给用户：先选账号/平台，
再面对空输入框，然后在“发送 / 生成内容”之间猜测。目标体验必须改为：

```text
今天可以做什么
→ 先了解 / 找选题 / 评估想法 / 直接制作
→ 有界参谋讨论
→ CreationProposalV1 方案确认
→ ProductionPackageV1 标准制作包
→ 修改 / 采用 / 批准 / 导出 / 人工发布
→ 品牌依据反馈
```

本包仍采用**绞杀者模式**：新能力按 feature 和新合同落地，旧页面在被替代时保留兼容，
不以“先拆完所有前端再做产品”为前提。

## 五、工程基础项（FE-01—FE-04）

### FE-01 · 正式路由、懒加载与应用内作用域切换（中）

- 引入 react-router 或经 Brief 批准的等价轻量路由；
- 业务应用按路由懒加载；
- 账号、平台和形式切换改为应用内状态与 URL 同步，不整页刷新；
- 删除 `navigateWithDraft` 的 sessionStorage 抢救机制；
- 草稿由页面 reducer 持有，必要时使用明确的草稿持久化合同，不再依赖刷新副作用。

验收：草稿不丢；全部旧 URL 兼容；浏览器后退/前进可预测；首包体积不增。

### FE-02 · 新合同 OpenAPI codegen 与流事件运行时校验（轻）

覆盖：

```text
context_selected
BrandBasisItemV1
BoundedAdvisorV1
CreationProposalV1
ProductionPackageV1
ContentDecisionProjectionV1
brand_basis_feedback
```

- 新代码零手写 API 类型；
- 流事件使用运行时 schema 校验；
- 未知、缺字段、乱序或非法事件显示安全错误并保留输入，不让页面进入半状态；
- 存量 63 处手写类型不强迁。

## 六、产品界面项（FE-05—FE-13）

### FE-05 · `/user` 今日工作台（中；承接 COMM-01 A3/A4）

首屏顺序：

```text
顶部：品牌 / 当前工作身份 / 个人菜单

今天先从哪一步开始？
[了解笛语] [帮我找选题] [评估一个想法] [直接制作]

为你推荐
2—5 张动态机会卡

继续进行
计划、最近成品、系列

当前品牌上下文
事实 / 表达边界 / 创作方法 / 商品事实 / 缺口
```

- 机会卡展示 why、basis、gaps、推荐平台/形式和制作难度；
- “讨论这个方向”进入 `/content` Advisor；
- “形成提案”进入 Advisor 的 proposal candidate 流程，但不直接建任务；
- 没有机会数据时仍显示四个起始动作，不用假数据填充；
- `/user` 不渲染 FT/SHA/Schema/能力矩阵。

### FE-06 · `/content` 有界创作参谋工作区（中—重；承接 A7）

桌面两栏：

```text
┌──────────────────────────────┬───────────────────────┐
│ 参谋对话与结构化方案          │ 当前品牌上下文        │
│ 用户问题                      │ 当前账号身份          │
│ AdvisorMessage                │ 可用品牌依据          │
│ Recommendation / Comparison   │ 商品与素材            │
│ Question / Gap / Proposal     │ 当前缺口              │
├──────────────────────────────┴───────────────────────┤
│ 输入框 [继续聊] [给我几个方向] [形成方案]             │
└──────────────────────────────────────────────────────┘
```

#### FE-06.1 结构化响应组件

- `AdvisorMessage`：自然解释；
- `RecommendationCard`：选题、受众回报、平台/形式、为什么适合、依据、缺口、难度；
- `ComparisonCard`：比较维度、每项取舍、推荐结论；
- `StrategyQuestionCard`：至多一个，可采用系统建议跳过；
- `KnowledgeAnswerCard`：系统知道什么、不知道什么；
- `GapCard`：阻断/非阻断缺口与去补入口；
- `ProposalCandidateCard`：形成 CreationProposal。

#### FE-06.2 交互边界

- 不以纯 Markdown 长段落代替推荐卡；
- “继续聊”永不建立正式任务；
- “形成方案”只请求 CreationProposal；
- 不再同时展示含义模糊的“发送 / 生成内容”双主动作；
- 平台/形式在参谋阶段可以是建议，不强制用户进入页面前选择；
- 多发布账号时，账号选择是上下文，不与平台和形式挤在一个过载顶栏。

### FE-07 · 品牌依据常驻面板与反馈入口（中；承接 A1/A2/A6）

- Advisor 阶段：显示当前可用品牌上下文；
- Proposal 阶段：显示“本次将使用”与“本次不会使用”；
- Package 阶段：显示每条 basis 的 usage_mode、impact、source_version、content locations 和 gaps；
- 公开 `basis_ref` 只用于反馈调用，不在界面展示内部意义；
- 每条依据提供：内容错误、已过期、与本次无关、缺少重要资料；
- 反馈回执明确“已提交给品牌管理员，不会直接修改历史内容或正式资料”。

`SourceStatusBadge` 用户文案：

```text
已确认来源
系统确定性编译
系统建议，需人工确认
当前不可用
```

禁止把“系统建议”显示为“品牌已确认”。

### FE-08 · 普通帮助与技术诊断分流（轻；承接 A4）

普通用户帮助：

- 笛语能帮我做什么；
- 系统当前知道品牌什么；
- 为什么建议这个方向；
- 怎样从讨论进入制作包；
- 当前缺什么资料。

管理员“技术诊断”保留能力矩阵、FT、SHA、Schema 和运行证据；不进入普通任务路径。

```text
确认      绿色
待补      琥珀
错误      深红
信息      蓝灰
系统建议  中性紫灰或蓝灰，不使用“确认绿”
```

### 7.4 字号与触控

```text
正文        ≥16px
辅助正文    ≥14px
元数据      ≥12px
按钮        ≥14px
表单标签    ≥13px
触控目标    ≥44px
```

禁止通过缩小到 0.62rem/0.64rem 解决顶栏拥挤。

### 7.5 动作层级

- 每阶段一个实心主动作；
- 次级动作用描边或文字；
- 胶囊仅用于主 CTA 和筛选标签，不让所有控件都成为胶囊；
- 品牌依据、资料缺口与来源状态优先于工程诊断信息。

## 八、移动端与可访问性

移动端必须完整完成：

```text
今日工作台
→ 找选题 / 评估想法
→ 参谋推荐与比较
→ CreationProposal 编辑与确认
→ ProductionPackage 阅读
→ 品牌依据反馈
→ 采用 / 导出
```

要求：

- 不只保留“对话 / 成品”两个旧工作面；新增“方案”阶段；
- 制作步骤和图文页序使用纵向卡片；
- 历史/项目入口不得因隐藏侧栏而消失，至少提供抽屉或项目入口；
- 抽屉/对话框焦点陷阱、Escape、关闭后焦点恢复；
- 200% 缩放无横向页面溢出；
- 局部宽表只能在自身容器滚动；
- 屏幕阅读器能够识别阶段、来源状态、错误和回执；
- 所有关键状态使用文字，不仅依赖颜色。

## 九、验收旅程与真实用户门

### 9.1 自动化与浏览器旅程

| 旅程 | 必须成立 |
|---|---|
| 首次进入 | `/user` 首屏可找到四个起始动作；无 FT/SHA/Schema；无空白画布 |
| 不知道发什么 | 不建 task/run/version；显示 ≥2 个差异方案与推荐原因 |
| 评估想法 | 返回比较/建议，不直接成稿；允许继续聊 |
| 形成方案 | Proposal 字段可编辑；确认前计数不变；token 篡改失败关闭 |
| 制作包 | 新成品零正则猜结构；视频/图文/DM01 分别按结构化字段渲染 |
| 来源状态 | “系统建议”与“已确认”视觉/语义明确不同 |
| 品牌反馈 | 提交后进入租户管理员队列，不进入 Ops 品牌裁决 |
| 决策 | 采用/导出/批准/撤回/人工发布均落追加事件并回读投影 |
| 移动端 | 完整完成参谋→方案→制作包→依据→采用，不丢功能 |
| 工程 | 切账号/平台不整页刷新；旧 URL 兼容；测试全绿或迁移对账 |

### 9.2 人类可用性门

至少 5 名目标用户，无培训完成：

- ≥80% 能找到四个起始动作；
- ≥80% 能理解推荐原因；
- ≥80% 能从模糊想法形成 Proposal；
- ≥80% 能说明本次使用了哪些品牌依据；
- ≥80% 能在制作包中找到台词、字幕、步骤、素材、发布配文；
- ≥80% 能提交品牌资料反馈；
- 记录首次形成制作方案耗时与“是否帮助我想清楚”的评分。

没有该记录，不得仅凭截图和 CI 宣称前端产品化完成。

## 十、明确不做

- 不做前端目录一次性整体重构；
- 不做 `CreatorApp.tsx` / `TenantAdminApp.tsx` 专项完全拆分；
- 不做全局 CSS token 合并与全产品重新皮肤；
- 不做管理端全量 IA 重排；
- 不建通用 Agent 控制台；
- 不建持久 CreativeBrief 编辑系统；
- 不做自动发布、媒体文件生成、空间效果图；
- 不做多级审批、评论线程和指定审阅人链；
- 不做价格、套餐、额度、点数、支付、账单、开票、自动续费或用量停机 UI；
- 不为了“像制作包”而前端补造后端没有的景别、音效、转场、资源或事实；
- 不强迁全部旧手写 API 类型。

## 十二、风险与回退

| 风险 | 缓解 / 回退 |
|---|---|
| 新页面继续堆进 CreatorApp | FE-00 + feature 边界；触碰功能先拆出再接入 |
| Advisor 退化为长段聊天 | 结构化响应组件和 schema；推荐/比较/问题有明确 UI |
| Proposal 看见与确认不一致 | token 失效提示、确认前后摘要对照、服务端权威验证 |
| ProductionPackage 只是重新排版 body | 新包必须含结构化 steps/script/subtitles/resources/status；旧 body 单独 LegacyView |
| 移动端再次靠隐藏功能适配 | 真实移动主链验收；项目/依据/方案均有替代入口 |
| 品牌建议与事实视觉混淆 | SourceStatusBadge 强制；确认绿只用于 confirmed_source |
| 技术诊断重新泄漏普通用户 | 路由和组件断言；普通用户 bundle 不加载 CapabilityMatrixView |
| 计费需求引发范围膨胀 | 明确不做清单；付费通过线下运营，不建任何收费 UI |
| 旧测试阻塞合理 IA 变化 | 允许迁移，必须旧→新旅程逐条对账，不许删测保绿 |
