## 1. 真实缺口与产品合同

UI-10 已证明 Reviewer exact evidence 与服务端事实裁决能够拒绝无依据机构主张和未标识
微事件；其 G3 阻断也证明现有 abstract-only 单元合同把题材型内容压缩成纯观点，无法合法
承载一般创作情境。

UI-11 不修改 Writer Prompt 来遮盖该缺陷，也不放宽真人事实边界。用户给出题材和限制已经
足以直接创作；系统自主选择纯观察或“观察＋明确假设情境”。没有真人事实时可创造一般、
假设性人物与动作，但不得绑定用户、真实家庭、品牌、员工、顾客、门店事件或经营历史。
真人事实仍由服务端逐字冻结；明确情境演绎仍走 dramatization。

## 2. 唯一最小结构修复

复用 CreativeKernelV1，只增加服务端所有、版本化且封闭的叙事程序：

- `observation_only_v1`
- `observation_with_hypothetical_example_v1`

第二种程序按可见顺序冻结抽象开篇、服务端假设范围、Writer hypothesis 情境和抽象收束。
Writer 仍只返回既定 `unit_id + text`；服务端使用一条版本化中性短语包裹 hypothesis。
Reviewer 必须审查包裹后的最终可见 clause，DeliveryCompiler 只能投影审查通过的文字。
该程序不得扩展为自由 DSL、题材表、人物表或第二套工作流。

## 3. 裁决与资源边界

- abstract 单元出现人物微事件时失败；
- hypothesis 只有在服务端完整可见范围内才允许一般虚构人物、动作与关系；
- hypothesis 绑定用户、真实家庭、品牌、真实员工、顾客、门店或经营历史时失败；
- 无依据机构主张继续失败，constraint 不能作事实许可证；
- 商品、品牌和真人事实只能来自 frozen fact，且逐字不变；
- 假设人物、场地、道具和声音不是生产资源；
- DeliveryCompiler 资源不足时只使用文字卡、旁白或已登记的一人条件；
- 新任务冻结 program id、Frame、事实单元、来源、reviewed digest 与 compiler version；
- 旧快照不回填、不改写，按既有 legacy 路径读取、修改、复制、导出、系列续写与跨平台改编。

program/Frame/fact/source/compiler 不变量、旧快照兼容和非固定成稿。对假设标识、真实主体、
资源污染和 G7 执行实际 mutation proof。

确定性门通过后冻结一个功能 SHA，只用当前 `deepseek-v4-flash`、温度 0、零重试且无
repository／数据库写入，依次执行 G3、G4、D1。G3 最多一次受影响可写单元修复；仍失败
立即 `BLOCKED`，不重跑、不换模、不形成第二策略。
