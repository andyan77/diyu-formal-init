## 2. 唯一结果

建立单一、服务端所有的 clause 权限链：

```text
NarrativeFrame + program + unit skeleton + fact kind + speaker kind
→ ClauseContextV2
→ occurrence-aware ReviewEvidenceV2
→ 服务端 subject / contract / grammatical evidence 裁决
→ 最多一次合法 affected-unit 修复
→ DeliveryCompilerV1
```

Writer 继续只返回 `unit_id + text`；Reviewer 继续只提取 evidence；DeliveryCompiler
继续只投影已审文字、中性短语和登记资源。模型、Writer 策略、事务边界与生产职责不改变。

## 3. 实现合同

1. `ClauseContextV2`
   - 保存 `clause_id/unit_id/exact_text/visible_order/text_source/unit_contract/speaker_kind/fact_ref`；
   - 每个 clause 恰好一个 contract；
   - program validator 与 semantic reconcile 共同消费同一 sidecar；
   - Writer、Kernel 自报类型和 Reviewer 类型均无授权权；
   - 未知 program/unit 或映射缺失结构失败。
2. `ReviewEvidenceV2`
   - 每个 span 使用 `text/start/end`，索引为 Python Unicode 字符位置；
   - 每个 clause 内增加 `grammatical_marker_spans.modality/aspect`；
   - 漏、重、额外 clause、原文/顺序/offset 不一致、伪 span 或 uncertain 均失败关闭；
   - V1 只作 legacy/历史 raw 读取，不回填。
3. speaker kind
   - 只接受 `institutional_account/personal_ip_account/unknown`；
   - 来自 ContentRole 结构化真源并冻结进新任务快照；
   - 旧行与旧快照保持 unknown，禁止按名称或画像散文猜测；
   - 个人 IP 可表达当前观点/建议，不能无事实声称经历、已发生、长期做法或具体对白。
4. 服务端裁决顺序
   - sidecar → evidence 资格 → wrapper/frozen fact 结构 → writer-owned subject →
     单值 contract + grammatical/event evidence → compiler provenance/resource；
   - frozen fact 和 server wrapper 不被普通语义规则二次否决；
   - `insufficient_evidence` 及结构、来源、事实、program、compiler、resource 错误不得送
     Writer 修复。

## 11. 主控恢复裁决：Strict Function Transport

上一节是 UI-12 第一次 Reviewer V2 资格的真实历史结果，不删除、不改写。主控进一步裁定：
失败根因不是 ReviewEvidenceV2 字段定义错误，而是普通
`response_format={"type":"json_object"}` 只保证返回 JSON，不提供 JSON Schema
完备性保证。UI-12 因此在原里程碑内从该历史 `BLOCKED` 恢复为 `ACTIVE`，不创建 UI-13
或其他 successor。

唯一实现变化：

- Reviewer V2 使用同一 `deepseek-v4-flash` 的受保护 `/beta` strict function call；
- function 固定为 `submit_review_evidence_v2`、`strict=true`，并用 `tool_choice`
  强制唯一调用；
- 只接受 `finish_reason=tool_calls`、恰好一个正确 function 和未经清洗的合法
  `arguments`；
- Reviewer 只接收 `text_source=writer_unit` 的 clause；server wrapper 与三类
  frozen fact 在调用前由服务端更强的来源、fact_ref 与逐字合同校验；
- Reviewer token 预算按 writer-owned clause 数使用确定性公式和固定硬上限；
- Writer、intake 和其他模型请求继续使用正式路径，不配置 JSON-mode fallback。

原 `18a0cd0…` raw 必须继续由严格 parser 拒绝；不得补 `implicit_subject`、默认
`uncertain=false`、搬运根级 `aspect`、发起 Schema 修复调用或随机重跑。Strict 确定性门
通过后，按第一包、第二包各一次执行真实资格；再继续原 UI-12 的 G3/G4/H1/D1、正式
API/PostgreSQL、完整工程门、CI 和生产闭环。

失败继续作为永久负证据。
