# 部署面浏览器脚本实跑记录 / Deployment-surface browser scripts

监理审查发现 5 指出：8 个部署面浏览器脚本「EXE-01 一个都没跑、零运行产物」。
本轮**逐个实跑**，全部对准 **loopback + 一次性可销毁本地库**，**未触碰生产 /
Qdrant / ECS / Dify / 任何外部服务**。本文记录每个脚本的真实结果——包括跑不通的。

**先说结论**：跑起来之后发现的第一件事，不是脚本的问题，是**EXE-01 把服务端渲染的
页面换成了 React SPA，8 个脚本全部还在按旧 DOM 的时序等待**。这是一处共因缺陷，
已修（见第二节）。修完 1 个脚本转绿，4 个继续在更深的位置失败，3 个缺私有真源无法
启动。**没有任何一个脚本因为本包（EXE-01R）的改动而失败——但这句话目前只有间接证据，
见第四节的诚实标注。**

## 二、跑起来之后发现的共因缺陷（已修）

**现象**：五个能启动的脚本，全部在第一步登录就死，报 `找不到输入控件
input[name="username"]`。

**测量**（不是推断）——用 CDP 直接读同一个页面的 DOM，同一次加载的两个时刻：

| 时刻 | `#root` 子节点 | `input[name=username]` | 页面文字 |
|---|---|---|---|
| `readyState === 'complete'` | 1 | **false** | `正在进入你的工作空间……` |
| 再等 1500ms | 1 | **true** | `品牌管理 / 登录笛语 / 用户名 / 密码 / 登录` |

**原因**：EXE-01 把 `/tenant-admin/login` 等页面从服务端表单改成了 React SPA
（`render_spa_shell`），旧表单退到 `<noscript>` 里——开了 JS 的 Chrome 根本看不见它。
真正的表单由 `AppRouter` 在异步引导完成后才渲染，而在那之前它先渲染
`LoadingPage`（`.page-loading`）。8 个脚本的 `navigate()` 只等
`document.readyState === 'complete'`，那一刻页面上只有加载占位符。

**修法**（一处共因，一处修）：等待条件补上「SPA 引导已结束」——

```js
`document.readyState === 'complete' && !document.querySelector('.page-loading')`
```

对非 SPA 页面向后兼容：`.page-loading` 不存在时条件退化成原来那条。

**效果**：`ux03-gate-b` 由 FAIL 转 **PASS**；其余四个越过登录、失败点前移到各自更深
的位置。`assert_test_reconciliation` 仍绿（断言数 549 → 646，只增不减）。

| 脚本 | 失败点 | 性质 |

R1—R5 任何一项，**故本轮不做**。

|---|---|---|---|---|

| `ux03-gate-d` | FAIL `无法点击 陈列搭配` | 同左，逐字一致 | 同左 | **EXE-01 时期既有偏离**，非本包 |

### 回归是什么

R3 的流校验把 `completed.result.target` 当枚举校验。它不是枚举。服务端
`content_service.py:2186-2187` 是**成对**发的：

```python
"target": _TARGET_LABELS[target],   # 小红书图文    ← 给人看的标签
"target_key": target,               # xiaohongshu_graphic  ← 标识符
```

于是 fail-closed 的门把**每一个真实成品**都判成「返回内容不完整」，页面停在安全状态。
本包新增的 35 条断言一条都没拦住，因为**夹具是照着同一个错误理解写的**——夹具里只有
`target_key`，从来没出现过服务端真发的 `target`。真服务器一跑就现形。

### 修了三处，都在本包已授权面内

1. `contentStream.ts`：`target` 按自由文本校验（仍须是字符串），`target_key` 保持枚举校验。
2. `types.ts`：`target` 类型由 `Target` 改为 `string`——原类型是个**谎**，R3 只是把
   一个安静的谎变成了响亮的谎。
3. `CreatorApp.tsx` `targetOf`：删掉 `?? version.target` 兜底。它会把「小红书图文」
   写进地址栏；服务端没给 `target_key` 时，留在当前作用域才是安全答案。

### 补上本该有的反证（+5，既有断言迁移不删）

- 服务端真实成对值（标签 + 标识符）必须原样通过；
- `target_key` 为 `小红书图文` / `weibo_post` / `""` 一律拒（它才是进地址栏的那个）；
- `target` 是自由文本，但非字符串仍拒。

既有那条 `target: ""` 断言**迁移到 `target_key: ""`**——同一个 violation、同一条保证，
换到真正承担风险的字段上，`target` 另有自己的类型断言。夹具也改成服务端真实形状，
从此每条走查都在跑真形状。

## 五、安全边界

- 全部实例：`127.0.0.1` 临时端口，`--host 127.0.0.1`，无对外监听。
- 全部数据库：项目自带 PostgreSQL（`var/postgres`，`listen_addresses = ''`，
  **没有 TCP 端口**），pytest fixture 每次新建、跑完销毁；另建的探针库
  `diyu_exe01r_probe` 已 `DROP DATABASE`。
- 全部外部依赖置为占位值：`DEEPSEEK_API_BASE_URL=https://example.invalid`、
  S3 指向 `127.0.0.1:9000`、生成器 `stub`。**全程未读 `.env`**，未连生产 / Qdrant /
  ECS / Dify。
