## 1. 结论先行

UI-07—UI-11 不是五个互不相关的模型 BUG，而是一条逐层暴露的责任链：

```text
持久化授权
→ 事实与约束分离
→ Writer 与成品编译职责分离
→ Reviewer 提证与服务端裁决分离
→ 来源、语态、主体绑定和证据组合
```

前四层已经形成可复用的结构边界。UI-11 当前真正未关闭的是最后一层：

1. `ReviewClause` 只保存 `unit_id/clause_id/exact_text/order`，服务端把
   `server_wrapper` 与 `writer_unit` 合并成相同的可见文字后，丢失了裁决所需的来源资格；
2. `abstract_principle` 被当成一个“任何 action/cause/result 都非法”的桶，泛指建议和一般
   因果因此被误判成已发生事件；
3. `ReviewEvidenceV1` 能证明某个跨度确实出现，不能证明该动作是建议、条件、可能性还是已经
   发生；它也不能凭空证明未返回的语义不存在；
4. 服务端尚未先按来源与 unit 合同冻结 `subject_binding`，就直接把
   `implicit_subject=current_speaker` 当作当前机构主张。
5. 相邻的 program 校验把 `observation_only_v1` 单 body 硬编码成
   `abstract_principle`，与服务端自己为 H1/D1 冻结的 `hypothesis/dramatization` unit
   冲突；两种合法结构都会先得到 `kernel_program_drift`。

因此，后继不能只改一个 `if`。推荐的最小闭环是：

- 服务端恢复每个 clause 的 `text_source` 与派生 `unit_contract`；
- 服务端从可信 scope、事实来源与 server-owned wrapper 派生 `subject_binding`；
- Reviewer 继续只提取精确跨度，但证据版本最小升级，**只新增一个顶层字段**
  `grammatical_marker_spans`，内含 `modality` 与 `aspect` 两组精确原文跨度；
- 服务端按本文件决策表组合裁决；无法证明的组合返回 `insufficient_evidence`，不得交给
  Writer 猜测性修复。

这不是修改 Writer 策略，不改变 DeliveryCompiler，不更换模型，也不放宽真人、品牌、商品或
制作资源边界。

### 7.1 组合优先级

服务端应按以下顺序执行，禁止后序覆盖前序资格：

1. **evidence 资格**：clause ID/原文/顺序/跨度/uncertain；
2. **来源结构**：server wrapper、frozen fact、writer unit；
3. **frozen fact**：唯一 fact_ref、逐字原文、可信来源；
4. **subject binding**：protected exact subject、可信 speaker、current person、generic/fictional；
5. **unit contract 与 server scope**：abstract、recommendation、hypothesis、dramatization、
   actuality reflection；
6. **语态证据**：modality/aspect 与既有 action/dialogue/cause/result/time/location；
7. **制作资源闭世界与 compiler provenance**。

任何步骤返回 `insufficient_evidence` 时停止，不调用 Writer 修复。Writer 只修明确属于可写 unit
的语义违规；来源错误、Reviewer 资格失败、frozen fact、program/compiler/resource 错误均不
可修。

## 9. ReviewEvidenceV1 充分性审查

### 9.1 它能证明什么

- Reviewer 确实返回了每个服务端 clause ID；
- `exact_text` 与服务端可见 clause 完全相同；
- 每个已返回 span 是 `exact_text` 的真实子串；
- Reviewer 明确观察到 subject、predicate、action/event、dialogue、motive、cause、result、
  time、location 或 implicit subject；
- Reviewer 是否自报 uncertain。

### 9.2 它不能证明什么

- span 没返回是否表示语义不存在，还是 Reviewer 漏提；
- 动作是建议、命令、条件、可能性、习惯，还是已完成事实；
- `了/过/着` 等体貌与“要/可以/如果/可能”等情态在裁决中的作用；
- 某个相同文字是服务端 wrapper、frozen fact 还是 Writer 自己写的；
- 显式人物是泛指、虚构角色还是真实当前人物；该绑定必须结合服务端 unit/source/scope；
- 叙事人物是否是制作资源；这只能由服务端资源注册表决定。

结构上的 `25/25` 或 `12/12` 只证明 clause 完整返回，不证明每个语义类别都无遗漏。

### 9.3 四句区分

| 句子 | V1 可见类别形状 | 需要的裁决 |
|---|---|---|
| “婆婆要尊重儿媳” | subject+predicate+action；无 time/location | 泛指建议，可在 recommendation 允许 |
| “婆婆尊重了儿媳” | subject+predicate+action；无 time/location | 已发生声称，无事实时拒绝 |
| “如果婆婆愿意先停一下” | subject+predicate+action；无 time/location | 条件推演，只在合法 hypothesis scope 允许 |
| “昨天婆婆停下来了” | subject+predicate+action+time | 现实事件，无事实时拒绝 |

第一、二句在 V1 的字段**类别形状完全相同**；第三句的条件性也没有独立证据槽。读取
`predicate_spans` 内的汉字再写专用词表，不符合本轮禁止范围，也不能形成稳定合同。第四句可因
time 证据被保守识别，但不能反向证明前三句。

结论：`ReviewEvidenceV1` **不足以完成稳定裁决**。

唯一必要的证据 schema 扩展是：

```json
{
  "grammatical_marker_spans": {
    "modality": ["必须是 exact_text 中的精确情态／条件跨度"],
    "aspect": ["必须是 exact_text 中的精确体貌跨度"]
  }
}
```

它作为 `ReviewEvidenceV2` 的一个新顶层字段；两组值仍只是原文跨度。Reviewer 不返回
observation type、subject binding、pass/fail、事实资格或修复建议。服务端仍是唯一裁决者。
V1 保留给已有快照/历史证据，不批量改写。

不建议新增 `possession_spans` 作为本 successor 的完成前提：当前必须处理的“我家/本店”可由
subject/location 与可信 scope 保守绑定，生产资源又由独立注册表裁决。若未来出现仅凭所有格
才能区分、且没有其他可用证据的真实反例，再单独证明必要性。

## 10. 仍不可判定的组合

下列组合不能在本轮伪装成 allow：

1. 零情态、零体貌、零时间的“婆婆尊重儿媳”——可能是泛指原则，也可能是习惯/现实声称；
2. Reviewer 返回完整 clause 但漏掉某个语义 span——服务端只能看到缺席，不能证明不存在；
3. 引号、否定、转述中的 protected subject/predicate，例如对禁写语句的元讨论；若 dialogue
   evidence 与作用域不能唯一覆盖，保守停止；
4. 不在可信 scope exact names 中的机构别名、门店简称或自然人昵称；
5. 同一“我们”在机构账号里究竟代表组织还是一组自然人；当前可信 speaker 为机构时按机构
   处理，业务若需另一语义必须先有显式作用域；
6. 没有 server-owned wrapper 的 Writer 条件句，即使自带“如果”，也不能自行获得
   hypothesis 资格；
7. 抽象隐喻被 Reviewer 提取为 action，但没有 modality/aspect/time/location 等进一步证据。

这些组合的当前唯一安全结果是 `insufficient_evidence` 或现有更严格的 reject，不得为了通过
G3 建中文题材/人物/句型词表。

## 12. 最小 successor 方案

经主控确认后，后继只需一个纵向变更：

1. clause 构造时把 server wrapper 拆成独立 clause，并在服务端 sidecar 中保存
   `text_source/unit_contract`；Reviewer 仍只看 clause ID 与 exact text；
2. 根据 program、unit ID/purpose、Frame 与 fact kind 确定性派生 contract/source，不让
   Writer 返回这些字段，不新增数据库表；
   同一派生结果必须供 program validator 使用，删除单 body 固定为 abstract 的分叉；
3. 从可信 scope、fact_ref、server wrapper 与 ReviewEvidence 派生 `subject_binding`；
4. 新增 `ReviewEvidenceV2.grammatical_marker_spans`，V1 留作 legacy；
5. 用 SDR 表替换“abstract 中 event_spans 非空即失败”的单条件；
6. `insufficient_evidence`、coverage/span/uncertain、source/fact/compiler/resource 错误均
   不进入 Writer 修复；
7. 先离线重放 EVD-014—020 与冻结正负样本，再按后继里程碑授权决定是否调用真实 Reviewer。

不改 Writer 输出、创作策略、模型、DeliveryCompiler 业务职责、数据库、OpenAPI、前端或生产。
具体文件边界见 [UI-12 候选实现范围](UI-12-候选实现范围.md)。
