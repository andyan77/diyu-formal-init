# 结构化反馈台账（手工 plan-B 口径）

> 用途：把陪跑中每一条真实反馈落成可决策的条目，直接喂 EXE-06 Brief。
> 口径：**手工维护**，不建产品侧反馈队列（那是 EXE-04）。
> 硬规则：**「处置」列不允许留空**，也不允许只写"已记录"——
> 必须写「改什么」，或者「不改 + 理由」。

---

## 一、会话表（每次陪跑一行）

| 字段 | 填写说明 |
|---|---|
| 会话编号 | `S<序号>`，如 `S01` |
| 日期 | YYYY-MM-DD |
| 租户 / 品牌 | 登记表中的指名租户 |
| 逻辑账号 | 本次使用的发布账号 |
| 操作者 | 登记表中的指名操作者（记岗位即可，不记联系方式） |
| founder 在场 | 是 / 否（本阶段必须为「是」） |
| 生成条数 | 本次实际生成条数 |
| 模型调用次数 | 含失败重试 |
| 会话结论 | 一句话 |

## 二、逐条内容表（每条生成内容一行）

| 字段 | 填写说明 | 来源 |
|---|---|---|
| 内容编号 | `S01-C1` | — |
| 题目来源 | `使用者出题` / `系统出题` | 陪跑观察 |
| 事实关 | `通过` / `有编造` | 使用者判断（辅导脚本关 1） |
| 像不像自己家 | `像` / `一般` / `不像` | 使用者判断（关 2） |
| 读者拿到什么 | `说得出` / `说不出` | 使用者判断（关 3） |
| `payoff_origin` | `server_assembled` / `static_fallback` | `inspect_task_value.py` |
| `payoff_degraded` | `true` / `false` | 同上 |
| `degradation_reason` | 降级时必填 | 同上 |
| `brand_relevance_path` | 降级时为空 | 同上 |
| 结论 | `可用` / `改了能用` / `不能用` | 使用者决策 |
| 不能用的归因 | `事实错误` / `不像自己家` / `没有回报` / `其他` | — |

## 三、问题条目表（**核心表**，处置列不得留空）

| # | 问题描述（使用者原话优先） | 来源 | 严重度 | 类型 | **处置** | 去向 |
|---|---|---|---|---|---|---|
| F01 | | S01-C1 | 高/中/低 | | | |

**列填写规则**：

- **严重度**：
  - `高` = 触发回滚条款（事实错误 / 跨租户 / 数据损坏 / 安全）或使用者明确"这样不能用"；
  - `中` = 影响可用性但有绕法；
  - `低` = 体验粗糙。
- **类型**：`事实性` / `品牌贴合度` / `价值表达` / `可用性` / `性能` / `边界认知`。
- **处置**（**必填，二选一**）：
  - `改：<具体改什么>` —— 写清楚要动的是哪个环节，别写"优化一下"；
  - `不改：<理由>` —— 必须给出真实理由，例如「属 EXE-06 范围，本阶段不动」
    「与 D-COMM-06 冲突，产品侧不做计费」「样本不足，再观察两次」。
- **去向**：`EXE-02` / `EXE-06` / `EXE-07` / `运营` / `不处理`。

> 反模式：处置列写「已记录」「后续跟进」「待评估」——
> 这三种写法一律视为**未处置**，台账不算完成。

## 五、隐私与留痕纪律

- 台账**存放在运营侧私有记录**，不进仓库；仓库内只保留本模板与聚合计数；
- 记录使用者**岗位**，不记录姓名与联系方式；
- 不记录使用者提到的**其顾客**的任何个人信息；
- 生成内容全文不进仓库；需要引用时只引用问题相关的最短片段，且去除可识别信息。
