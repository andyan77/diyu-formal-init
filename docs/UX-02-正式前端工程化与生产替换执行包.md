## 3. 两条承重旅程

### A. 管理员开通租户用户

正式 React/API/PostgreSQL 与两个隔离浏览器会话连续完成：

管理员登录 → 创建自然人身份 → 选择互斥入口资格 → 分配组织、内容或 DM01 资格 →
分配合法发布账号与平台目标 → 获得可信公开域名生成的完整 HTTPS 一次性链接 → 新会话设置
密码并从正确入口登录 → 仅看到获准范围 → 管理员停用 → 旧会话和再次登录失效 → 精确清理。

创建成员、重设密码和运维开通首位管理员均以 additive 字段返回完整 HTTPS URL；链接不得依赖
请求 Host 拼接。一次性、失效、会话撤销、错误恢复和 `/activate/` 安全日志边界保持。

### B. 租户用户低种子创作

正式 React/API/PostgreSQL 与既有 DeepSeek 生产适配连续完成：

登录 → 选择获准发布账号 → 同账号选择平台/形式 → 输入低种子 → 显式生成完整 V1 →
自然修改 V2 → 回读 V1 → 返回当前 V2 → 复制/导出当前查看版。

“发送”只交流且不创建任务或版本；“生成内容/修改成 Vn+1”才进入持久化。可选创作方向覆盖
题材、讲法、风格、形式、系列和互动，并支持不选、常用项、更多/搜索、自然语言自定义与清除。
加载只展示真实生命周期，失败、429、断网、会话过期及账号/平台切换均保护输入和既有成品。

## 9. 真实偏差与边界

- 第一个生产部署候选因 root-only shell 继承 `umask 077`，checkout 源文件为 0600，非 root
  构建失败；旧镜像及时恢复。随后先补 checkout 权限归一化，再把安全 umask 提前到 checkout
  之前，最终旧镜像回退在相同继承条件下通过。
- 首轮生产激活页面因 `Referrer-Policy: no-referrer` 产生同源 `Origin: null`，被 CSRF
  中间件拒绝；修复只接受 `Sec-Fetch-Site: same-origin` 的 null origin，跨站和恶意
  origin 继续拒绝。最终 CI 与生产激活旅程通过。
- 初次生产浏览器夹具错误地把平台显示名写成具体形式，移动夹具又未预置版本历史；两次均在
  模型调用或业务写入前停止，修正验收 oracle 后只执行有效旅程。
- append-only 内容版本不能由应用角色删除，生产 synthetic 清理因此使用部署前备份原子
  恢复。隔离恢复数据库最初丢失 migrator owner/ACL，部署在切换前失败且旧候选持续健康；
  只把 public 业务对象和数据库 owner 恢复到既有 migrator 边界后部署成功。

  市场差异、企业 SLA 或 20/55/44 全组合稳定支持。运行资产仍为 `41`，候选 `243`，
