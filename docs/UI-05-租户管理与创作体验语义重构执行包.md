## 1. 真实结果

租户管理员应清楚知道“我管理谁、谁在使用、缺什么、影响什么、如何补”；创作者应在一个
发布账号下直接选择平台和形式，不把平台载体误认成另一套账号或人设，并在生成期间看到可信
过程状态。产品页面不暴露数据库对象、内部权限词、工程证据或验收过程。

## 2. 冻结语义

1. 登录账号代表自然人与入口资格，不是企业发布账号；管理员身份不自动成为发布身份。
2. 用户只看到逻辑“发布账号”：名称、品牌与负责团队、唯一当前 ContentRole 内部分类、
   唯一版本化五段账号画像、可操作成员和一个或多个平台目标。
3. carrier rows 继续作为兼容物理实现，普通 UI 不展示其名称、父子 ID 或物理行数。
4. 平台是本次内容目标。页面显式选择优先于账号默认和服务端稳定默认；自然语言不静默覆盖
   页面选择。
5. ContentRole 只作为内部稳定类型或画像短标签；原表达边界并入画像第二段。画像只归逻辑
   发布账号，跨平台新建读取当前画像，重编译与旧任务继续使用冻结画像。
6. 内容和陈列继续是参考建议，不增加确认、审批、授权或责任流程。

## 3. Gate A：本次交付

静态原型位于 `docs/前端UI架构/产品化HTML原型_UI-05/`，包含独立评审壳和八张代表页面：

1. 租户管理概览；
2. 团队使用；
3. 成员与入口资格；
4. 发布账号详情；
5. 品牌资料库；
6. 当前可用与待补；
7. 内容创作空状态；
8. 内容生成进行中及完整成品。

原型必须直接使用正式 VI，离线可浏览，支持 `1440×900` 与 `390×844`，没有外部请求，
产品页不含评审控件。所有按钮都落到页面、抽屉、弹窗或稳定状态；不放平台连接、自动发布、
账单、实时监控、OCR、知识图谱、自动激活、取消生成或其他 Gate B 不准备实现的动作。

Gate A 只冻结产品方向，不证明正式 API、React、数据库聚合、流式响应或生产替换已经完成。

## 4. Gate B 前承重预检

仓库只读核对确认 root account 与 carrier rows 原则上可以无损聚合，但正式实现前必须在生产
做一次零写入预检：

- 每个启用根账号恰有一个当前 ContentRole；
- carrier 指向同租户、同品牌的根账号，组织与角色关系没有漂移；
- carrier 没有需要保留或迁移的独立五段画像；
- 根账号与 carrier 的成员授权差异可以无损解释；
- 多根账号自然人的显式账号选择不依赖客户端猜测；
- 历史系列、任务、版本及平台父子关系可继续读取。

任何冲突都不得用 `LIMIT 1`、名称裁剪、画像复制或删除历史行掩盖。
